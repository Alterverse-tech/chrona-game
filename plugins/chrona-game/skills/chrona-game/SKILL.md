# Deliver a game to Chrona

For a combined creation-and-upload request, first develop the requested game using the coding agent's normal workflow and the user's chosen tools. Preserve the intended gameplay, art direction, assets and quality. The delivery contract belongs to the subsequent integration stage; do not read it or initialize the bundled starter before deciding how to build the game. The starter is optional for users who specifically want that scaffold.

When a playable game is ready, read [the package contract](references/package-contract.md) and prepare a separate delivery copy or a focused integration change. Keep a working original for comparison. Adapt assets, readiness, selection and account saves at explicit boundaries. Do not silently remove effects, replace artwork, change controls or downgrade dependencies to pass the importer. If the existing platform cannot host a required feature, identify that concrete compatibility gap instead of claiming an equivalent delivery. The current v1 importer recompiles supported browser sources; it is not a universal unchanged-build hosting service.

1. Add `chrona.game.json` with a stable package ID. Connect the v1 scene and gameplay entry points to actual game behavior, retaining the rest of the source structure. Read the game's coordinate system rather than assuming every game is a city or Pocket Planet. Include enough source context for the platform Agent to continue development.
2. Use the `chrona` SDK at the integration boundary. Register initialization before reporting ready; preserve the original save schema with the generic JSON protocol when appropriate. Assets remain content-addressed resources. Never include credentials, `.env`, browser account state, node_modules or build caches. Keep asset provenance with the delivery when relevant.
3. Run `node <skill>/scripts/game-kit.mjs check <delivery-directory>` and `node <skill>/scripts/game-kit.mjs pack <delivery-directory> <output.chrona-game.json>`. Keep the original project's preview workflow. The optional v1 preview helper and exact supported dependencies are described in the contract. Package checks establish structure and hashes; the platform importer performs the actual build.
4. Complete the upload when authorized and browser tools are available. Use the target Chrona site and the user's normal sign-in. From Create, select New World → Start With → Import a Game Package, choose the package, and import. This creates an owned private World with scene, gameplay and advanced code editing enabled. An already-created blank World can instead use World Development → Draft Workspace → Upload Game Package. For updates, use that existing World and retain its package ID; do not create duplicates after a recoverable upload failure.
5. Verify the actual imported preview and expose its World Studio link. The World uses the platform's ordinary members, development settings, source revisions, Agent, drafts and release controls. Upload creates a draft; use Launch World or Release Update only when release is requested. Public access remains a separate setting. Do not assert multiplayer or another game-specific capability merely because it exists elsewhere on Chrona.
6. Report the World URL and local source/package paths, actual draft/release status, material integration changes, and checks performed. When requested, demonstrate continued editing through the World's own Agent and version history. Distinguish browser gameplay evidence from package/build checks. If browser access or sign-in is unavailable, give the ready package and the specific remaining upload step; do not claim upload completed. This skill currently uses browser upload, not a CLI token or direct-upload endpoint.

The zip is portable: extract this `chrona-game` folder into `~/.codex/skills/` for Codex or `~/.claude/skills/` for Claude Code, then invoke `$chrona-game` or ask to use the Chrona game skill. No platform repository checkout or model API key is needed to package a game. Upload uses the user's normal web login.
